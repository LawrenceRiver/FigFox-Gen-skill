# FigFox-Gen-skill

Turn a scientific Methodology into one source-grounded PNG1. V2 is the default workflow below. Initialize `input/style-brief.json` for every new run; if no image reference is supplied, use `model_composed`, a null main reference and empty detail/attachment lists. Never fall back to V1 because a new run lacks a file. Original V1 remains separately installable and explicitly callable as `$figfox-gen-v1`; see [versions and migration](references/versions.md).

## 1. One peer-and-Methodology pass: the visual-needs anchor

Read Methodology and inspect actual figures from about two similar scholarly examples. In ONE synthesis, list only visual conventions that the examples share AND this Methodology actually needs. Check input/output representation, real specimens or thumbnails, internal topology, intermediate artifacts, iteration/comparison views and meaningful visual symbols. A PDF may use source pages, HTML a rendered page thumbnail, a graph actual topology; never add one just because a peer has it.

Keep this anchor in Context1's conventions: concept, observed peer commonality, Methodology relevance and useful visual form. Give selected needs stable IDs in the generation plan's `visual_needs`. Do not produce a second long paper summary or run another generic visual survey. A method-specific scientific detail remains in Context2; do not invent a peer commonality for it.

## 2. Parallel work from that one list

After the list exists, run independent work together:

- For each visual need, decide whether a suitable existing visual asset would communicate it more clearly, naturally or faithfully than redrawing it. This is an open-ended decision, not a fixed list of media categories. Collect the actual file when direct use is appropriate, inspect it, and classify it as direct content, a crop of direct content, or construction/style evidence. Concrete samples, views, interfaces, instruments, maps, scans, renderings and outputs are examples, not a whitelist. Native diagrams remain appropriate for abstract relations.
- Find effective icon/illustration constructions for the listed needs. Prioritize scientific input/output, difficult symbols and meaningful small views. For a standard model actually named in this Methodology, prefer its established, source-checked architectural drawing grammar at the selected detail level. A small recognizable U-Net or Transformer inset may suffice; do not invent a mirror-trapezoid or arbitrary gadget to stand for it, and do not expand unchanged internals beyond the innovation-led hierarchy. Reuse an already inspected source/crop; resolve a missing canonical construction within this same parallel retrieval task, not a new search round. Do not search separately for every component or make a generic PDF/robot/code icon the default answer.
- Inspect a main style reference. State exactly what is liked: typography, line character, frame grammar, spacing, colour relationships or arrow treatment. For arrows, name the liked shaft character, head/body proportions, weight, corners and palette role; a bold hand-drawn rod, filled or rounded arrow can be appropriate, not only thin black connectors. It is not permission to copy the whole source composition. If two references complement each other, give each an explicit trait/role. Use user references or local FigureBench/FigFoxBench when suitable.
- Match the approved palette group using the existing restrained colour principles. This may proceed alongside stylistic/creative work once liked traits are clear. Keep approved colour direction stable.

Reuse source-checked caches. Keep full source/crop/license evidence local. Drop rejected candidates and repeated research prose from handoffs. Search again only for a named unresolved visual need. Canonical architecture, title treatment and arrow style are decisions inside the existing retrieval/Director work; do not add model calls, separate surveys or an extra style-sheet image for them. Do not create separate C/reverse-C routing research: Creative Director should understand those ordinary layout patterns.

## 3. A grounded drawing correspondence, not another search round

For each selected visual need write one row: **need ID / location → observed borrowed construction → how our own scientific content is drawn**. These are `local_visuals` with `need_id`, target component, meaning, construction and source basis. `visual_needs` must be covered; unknown/missing need IDs fail compilation. Need IDs are not a requirement to retrieve an image for every graph component. The correspondence also records whether an asset is directly used, cropped, or only borrowed from. Direct-content material is not a style reference: retain its actual content rather than asking the generator to imitate it. Use [direct visual insets](references/direct-visual-insets.md) for collection, placement and optional deterministic compositing. Never substitute another study’s results for this method’s evidence; illustrative material stays explicitly illustrative.

Context2 independently preserves exact scientific components, labels and directed relationships. Context3 retains inspected construction evidence and the selected palette. Keep scientific assumptions, fixed/trainable status, input/output types, gate inequalities and data-isolation boundaries explicit. Full research is not sent to the image model.

## 4. Creative Director + palette: settle one coherent visual system

Run one Creative Director ideation pass with the needs anchor and correspondence table. Combine reference traits into one construction language, not a collage. Make useful visuals prominent; do not reduce the method to empty equal cards. A planner should visibly plan something, a candidate show its actual artifact type, and inspection display real paired views when the method requires them.

Before imagining local icons or model internals, imagine the entire structural overview as one clean rectangular silhouette. Choose a concrete organizing rule from equal-width stage columns, equal-height parallel bands or balanced bilateral groups, according to the scientific graph. Equalize peer regions, margins and gutters. Symmetry is visual organization, not permission to invent a branch or a false shared bus; innovation can span integer grid cells. State the chosen rule before local drawing decisions. Fix the whole canvas and regular row/column framework first. Reserve the final output inside the same footprint; align sibling block edges, baselines and repeated objects. Innovation groups may span cells, without making the overall silhouette ragged. If the final stage would protrude, simplify/reflow preceding content or rearrange within the grid; do not extend a dangling final stage below or outside the figure. Keep steps simple and the composition squarely aligned.

Plan placement and arrows together. Align intended ports on a shared horizontal or vertical axis wherever possible. Use a coherent arrow family; keep head/body proportions and weight consistent within each role and scale, including local microviews. Route points specify the centerline, not a mandatory thin-black stroke. Reserve clearance for the selected shaft and arrowhead width; after labels/icons are placed, trace every shaft end-to-end once more. Straight connectors first; move modules to remove crossings and pointless bends. A person must be able to reproduce each arrow as one continuous source-border → target-arrowhead path. No empty-space starts, detached arrowheads, suddenly disappearing shafts or text-erased gaps. Use short branches and one clear perimeter lane for an actual return loop. Only after layout alternatives fail may an unavoidable crossing use a continuous bridge, modest rerouting, or distinguishable approved ink colours. Preserve every scientific edge. If a model frame contains several processes, the visible landing must reach the intended process subregion; a recurrent inference loop cannot enter a neighboring training inset just because they share a frame. Record exact ports/routes once the layout is coherent. Every new run uses `figfox-generation-plan-v2` with `routing_geometry`: bounded canvas, row/column tracks, one grid slot per Context2 component, route kind and explicit orthogonal path points. Run the deterministic preflight through both prompt builders before generation. It rejects detached endpoints, node obstruction, unapproved crossings, shared target landings, excessive bends and needless detours. Fix the layout when it fails; do not downgrade the plan to V1 to bypass a failure. Reserve section-heading bands separately from connector corridors; pale fills and title bands must not erase shafts. Put visible connector captions in reserved boxes beside the shafts. See [geometry schema](references/compact-generation.md#v2-grid-and-route-preflight).

Use concise reader-facing scientific headings derived only from the current Methodology. Never transfer stage titles or operations from another case or the Skill workflow into a scientific figure. Keep internal phase codes such as G1/G2 in planning/provenance. Use `display_labels` to shorten component captions while preserving their IDs and source meanings. Image text should be names, essential terms and equations, with short relation captions only where needed. Keep long explanations outside the figure. No visible underscore is allowed, including identifiers and illustrative code. Typeset indices as real subscripts/superscripts or use a concise scientific alias. Keep raw code, filenames and object IDs unchanged in internal records, not on the image. Creative Director supplies `notation_map` original → approved display pairs and checks all visible text; unmapped underscore forms stop Prompt1 compilation. Optically align text baselines, repeated objects, shared edges and centers with consistent spacing. Shorten text or improve placement before shrinking fonts.

Purple/blue/orange was an example of colour relationships, not a fixed theme. Select a compatible library group independently for each task from the liked reference traits, saturation and contrast needs. A task may reuse a similar palette when appropriate; do not force variation or carry the last demo's hues forward as default. Lock exact hues only on explicit user instruction. Once selected, keep the current run internally consistent.

Allocate colour fill to the important mechanism, meaningful representation or content region. Titles default to bold black/dark text or a deliberate theme-coloured label on the ordinary background; do not automatically paint a coloured header strip behind each title or use white-on-colour title tabs. A specific explicit author/reference choice can justify an exception, but the example gallery is not permission to reproduce its title bars.

Use the existing palette rules: related pale base regions, deeper meaningful marks, usually 1–2 dominant families and one separated contrasting focus where needed. Dark/black labels are welcome. Keep typography coherent with the liked reference traits; no gray microcopy or automatic Times New Roman. Necessary short italic notes use readable dark Arial Italic. Default to short unnumbered stage names; do not add step badges or stage counters. Explicitly requested numbering or genuine paper panel labels are separate author requirements. Semantic hand-drawn/native objects are welcome; pasted mascots, badges and generic decorative AI symbols are not.

## 5. Compile one drawing packet, generate, inspect

Use [compact-generation.md](references/compact-generation.md) for exact artifacts/schema/commands. The packet contains: short scientific invariants; overall framework; exact components and arrows; the needs-to-drawing table; liked main/font/detail reference traits; actual selected reference images with dimensions and scoped contracts; palette; final Creative Director construction decisions. It does not contain full PDF text, search transcripts, rejected candidates or duplicate Context JSON.

```sh
python scripts/figure_workflow.py check-installation --root .
python scripts/figure_workflow.py build-creative-director-prompt --run RUN
# Calling Harness performs one real ideation pass, saving brief.json.
python scripts/figure_workflow.py build-prompt1 --run RUN
# One image-generation call with prompt.md and actual manifest attachments -> PNG1.
python scripts/figure_workflow.py validate-run --run RUN
```

The skill uses one image-generation pass. When approved direct-content raster assets are selected, reserve clean inset slots and composite the collected files into the actual generated layout with the optional deterministic helper; that composite is final PNG1. Keep the raw layout and source assets. This placement step does not redraw content or call a second model. Otherwise the generated image itself is PNG1. There is no automatic second image, conversion or repair loop. An explicit user request for another comparison or connector repair is a separate recorded operation; preserve the prior image and actual prompt. File/provenance validation is not proof of scientific or aesthetic correctness. Inspect the actual output before calling it accepted.

Load [style-first.md](references/style-first.md) only for family/reference permission/colour details, [artifact-schemas.md](references/artifact-schemas.md) for original artifact schemas. Source availability or dataset membership alone is not redistribution permission. Keep user images and unresolved assets local. Never copy a reference's labels, scientific claims, photos or mascots into a new method.
